# TeamsExam 需求：约考管理与考试券管理

TeamsExam 是拟基于 GeminusAdmin 建设的认证考试管理系统，功能尚未实现。同一应用包含约考管理和考试券管理两个独立业务模块，面向培训班学员的持续认证考试业务，不是一次性活动。

应用将通过 GitHub 的 Fork 功能从组织中的 GeminusAdmin 底座仓库创建业务仓库，仓库名称待定；两个业务模块均不加入底座通用 Admin 模块。本文中明确标为“建议”或“待确认”的内容不是已确定的实现范围，须在实现前确认。

## 仓库与分支

- 保留 GitHub Fork 关系，以 GeminusAdmin 底座仓库作为上游。
- 保留 `main` 分支，仅用于跟踪上游 `main`，不合入 TeamsExam 业务开发改动；在 GitHub 页面上选择 `main` 分支，通过 **Sync fork** 同步该分支的上游更新。
- `teams-exam` 从 `main` 创建，作为业务开发主线和 GitHub 默认分支。上游更新同步到 `main` 后，再将 `main` 合并到业务分支，处理冲突并验证兼容性；不将业务改动合入 `main`。
- Fork 的可见性遵循 GitHub 规则：公共底座的 Fork 也为公共仓库，业务代码放在独立分支不会使其私有；私有底座的 Fork 保持私有，并受组织及企业的 Fork 策略约束。

## 系统目标

采用 **“AI 优先交互，业务核心确定，关键界面保留”** 的建设方向，不将系统限定为传统菜单和表单，也不以 AI 替代可靠的业务规则与数据管理。

- AI 优先交互：优先利用自然语言表达意图、理解邮件和凭证、查询解释及提出建议，按任务展示结构化结果，不要求所有操作都通过聊天完成。
- 业务核心确定：权限、业务规则、时间冲突、资源容量、考试券分配、事务一致性及审计由业务系统负责。AI 通过受控业务能力查询或提出操作请求，不直接修改数据库，也不自行决定业务规则或操作授权；执行结果以业务系统记录为准。
- 关键界面保留：保留考试时段与容量视图、考试券库存、审批、变更预览和审计等必要界面，用于批量核对、异常处理及人工接管；AI 不可用时，已支持的业务仍可通过人工操作完成。
- 底座能力优先：约考和考试券模块优先复用 GeminusAdmin 已提供的身份认证、权限、界面组件、数据处理、导入导出、通知、审计等能力，不重复建设通用机制。底座能力无法满足已确认的业务规则时，才在业务模块内补充最小必要实现，并说明差异原因；不为复用而改变底座能力原有语义。

这是系统总体目标，不自动扩大首版范围。首版 AI 能力仍为官方确认邮件或凭证的辅助提取，并经人工确认后保存；自然语言查询、操作建议及执行能力的具体范围与授权策略须另行确认，AI 自主程度来自明确的业务授权，不来自模型判断。

## 共用身份与访问约束

- 复用底座的 Microsoft Entra 登录、用户和权限能力，不另建一套身份系统。
- 学员通过机构组织账号登录；成功登录不等于获得管理权限，也不自动证明所属培训班。
- 服务端必须检查操作权限和记录归属，不能通过修改记录编号读取或修改其他学员的数据；管理员按授权的数据范围操作。
- 内部 Entra 学员身份与官方考试账号分别记录，不要求二者邮箱一致；内部组织账号登录不等同于官方考试账号注册。
- 学员接入、培训班关联方式、管理员的数据范围，以及官方考试账号需记录的字段待确认。

## 约考管理模块

### 业务定位

采用“考试计划 → 意向申请 → 资源预占 → 内部审核 → 官方预约确认 → 变更与闭环”的管理模式，分别管理学员考试意向、机构资源安排和官方预约事实。

实际预约在考试官方网站完成。本应用负责内部安排、资源预占、结果记录和冲突检查，不代替官方预约系统，也不保证官方考位可用。

### 首版范围

- 管理员建立考试时段，分别配置机位和人员容量。
- 学员提交并查看自己的考试时间意向；管理员审核，系统按规则预占或释放资源。
- 学员提交官方预约结果，管理员核验实际考试时间及凭证。
- 服务端检查同一学员考试时间冲突、机位容量和人员容量，并保证并发操作不突破容量。
- 使用机构已有 Azure 模型服务辅助提取官方确认邮件或凭证，人工确认后才能保存。
- 首版不包含课程时间冲突检查、AI 自动排期、自动登录官方网站或自动完成预约；是否记录实际参加、缺考等结果待确认。

### 管理记录

建议按以下业务对象组织记录，最终字段在实现前确认；业务对象不意味着必须分别建设模块或数据表。

| 记录 | 主要内容 |
| --- | --- |
| 考试项目 | 认证名称、考试代码、时长、考试方式、官方预约平台 |
| 考试时段与资源 | 日期、时间、地点、机位容量、人员容量、开放状态 |
| 学员意向 | 学员、培训班、考试项目、期望时段、审核结果 |
| 资源占用 | 对应意向或安排、占用时段、机位及人员数量、释放情况 |
| 官方预约记录 | 官方预约编号、实际考试时间、预约凭证、核验结果、可选考试券关联 |

### 管理流程

1. 发布计划：管理员配置考试时段和资源容量；适用学员范围待确认。
2. 提交意向：学员选择时段，服务端按最新数据检查时间冲突和容量；提交成功即预占资源，不等待审核通过。
3. 内部审核：管理员审核安排；通过保持原占用，不额外扣减，拒绝或取消释放预占资源。
4. 官方预约：学员在官方平台完成预约，提交实际考试时间和凭证；可以人工录入，也可以使用 AI 辅助提取。
5. 核验安排：管理员审核官方结果，重新检查冲突及资源容量；结果与意向不一致时进入待明确的调整流程，不得静默覆盖原安排。
6. 变更与闭环：处理改期、取消及异常，建议保留变更历史；具体流程及闭环标志待确认。

AI 提取结果作为待确认信息展示，人工核对和修正后才能提交保存。AI 不直接写入预约事实、审批结论或资源占用；未识别、缺失或存在歧义的信息不得编造。保存时仍执行与人工录入相同的权限、字段、时间冲突和容量校验，提取失败时仍可人工录入。

### 状态与规则

建议区分以下状态维度，具体名称及流转规则待确认：

| 状态维度 | 首版处理方式 |
| --- | --- |
| 内部审核 | 待审核、已通过、已拒绝；取消另行记录 |
| 资源占用 | 预占、正式占用、已释放；预占转为正式占用只改变性质，不重复扣减容量 |
| 官方预约 | 未提交、待核验、已确认；改期或取消保留历史，不直接覆盖原记录 |

- 审核通过不代表官方预约成功，上传凭证不代表已经核验。
- 提交、审核以及任何影响考试时间或资源占用的修改，均须在服务端按最新数据检查学员时间冲突、机位容量和人员容量，不能只依赖页面提示或提交前查询。
- 并发申请不能超出容量；重复提交或重复审核不能重复占用，重复拒绝或取消不能重复释放。
- 官方结果必须记录可核验的考试时间。官方预约事实与内部安排分别管理，不符合内部时间或容量规则的结果不能直接被视为内部安排已确认，也不能被标记为从未发生的官方预约。
- 改期需保证旧资源释放与新资源占用的一致性，不能出现部分成功；具体调整、审核及失败处理流程待确认。

### 权限与敏感信息

学员只能提交和查看获授权的本人意向及官方预约结果；管理员按授权范围维护时段、容量并审核提交。

官方邮件、预约凭证及 AI 提取结果涉及个人信息。接入模型前须明确允许发送的数据范围、机构隐私要求，以及输入材料和提取结果的存储期限。

### 验收要求

1. 学员通过机构 Entra 账号登录，只能访问获授权的业务入口和自己的记录；管理员按授权范围审核和维护时段。
2. 提交意向成功后产生相应资源预占；同一学员的重叠考试安排、机位不足或人员容量不足时，提交失败且不产生部分占用。
3. 多人同时争用剩余容量时，成功提交的总占用不超过容量；重复提交或重复审核不能重复占用，重复拒绝或取消不能重复释放。
4. 拒绝或取消后，释放的容量可被后续提交使用；审核通过保持原预占，不额外扣减。
5. 官方预约结果与内部意向可区分，审核时能核对官方时间；不一致的结果不能通过直接覆盖绕过冲突检查。
6. AI 提取的信息在人工确认前不改变预约事实和容量；人工修正后的提交仍受全部业务规则约束，提取失败不阻断人工录入。

建议状态、改期及异常流程确认后，再补充相应验收条件，不以建议状态推定已确定的业务流转。

### 待确认事项

- 支持的认证考试、考试时长、考试方式、时区、时间重叠边界及缓冲要求。
- 人员容量的业务含义、每名学员所需机位和人员资源、是否跨时段共享资源、重叠时段的容量计算方式及容量变更规则。
- 提交、审核、拒绝、取消和重新提交的具体流转，预占是否超时释放。
- 官方结果与意向不一致、官方改期或取消时的资源处理、审核及异常处理规则。
- 建议状态、变更历史及闭环方式，是否记录实际参加、缺考等结果；这不表示首版包含成绩管理。
- Azure 模型部署、可用接口、输入格式、允许发送的数据范围及邮件、凭证和提取结果的存储期限。

## 考试券管理模块

### 业务定位

考试券由机构从代理商采购，再分发给学员用于官方考试预约。模块由内部人员管理采购批次和单券记录，并登记接收学员及人工核验的使用情况。

考试券管理是同一应用内的独立模块，不作为约考记录的附属功能，不要求先创建约考意向或官方预约结果才能管理考试券。

本模块仅供获授权的内部人员使用，不向学员或外部用户提供入口或自助操作；内部人员可以将已确认的内部学员账号，或仅以姓名和邮箱登记的外部用户，记录为考试券接收人。

### 首版范围

首版包含独立管理入口、采购批次维护、考试券批量导入和查询、登记内部学员或外部用户为接收人、人工核验使用情况、库存统计、到期前一个月提醒及操作记录。

本模块仅供获授权的内部人员使用；学员登录、自助查看、领取确认或提交使用结果均不属于范围。采购审批、财务付款、自动核销及与约考记录关联不属于首版。

### 管理记录

首版记录以下信息，不扩展为采购或财务管理：

| 记录 | 主要内容 |
| --- | --- |
| 采购批次 | 代理商/发券方、批次标识 |
| 考试券 | 所属批次、券码、代理商提供的适用考试/地区和有效期、当前接收人（内部学员或外部用户姓名和邮箱）、分发状态、使用核验信息 |

每张券只记录当前接收学员，不支持退回、转让或重新分发。分发和状态变更应保留操作记录。

采购批次维护补充约定：批次标识全局唯一；内部人员可新增、查看和编辑批次，仅不含考试券的批次可以删除。

### 管理流程

1. 采购批次：内部人员维护发券方及批次标识。
2. 批量导入：内部人员按 CSV 模板将券码、有效期及代理商提供的适用考试/地区信息导入对应批次。任一行校验失败时整批不导入，并报告错误行及原因。
3. 分发登记：内部人员选择接收学员账号，或填写外部接收人的姓名和邮箱；同一张券不能同时分配给多人，也不支持重新分发。

内部接收人从现有用户账号中搜索，由操作者确认该账号属于接收学员并关联该用户；账号能够登录不代表学员身份，系统不推断培训班或学生身份，已删除账号不能作为新接收人。外部接收人只记录姓名和有效邮箱，不创建账号、不发送通知，也不提供自助入口。
4. 使用确认：内部人员根据官方预约结果和凭证人工核验并登记；不调用官方接口自动查询或核销。
   首版登记是否已核验使用；已核验时填写简短依据说明（最多 255 字），不填写券码、不上传凭证。可更正说明或撤销核验，撤销时清除说明；不要求已分发或未过期。并发修改时提示重新加载，操作审计仅记录基础写操作信息，不采集提交内容。
5. 库存统计与提醒：查询未分发、已分发及已核验使用情况；在有效期到期前一个月提醒内部人员。

到期提醒采用务实默认：每天使用 UTC 日期，从到期日前一个自然月（上月无对应日期时取月末）至到期日（含）向当前拥有 `exam-vouchers.manage` 权限的非删除内部用户发送站内通知。窗口内导入或恢复运行时补发；每人每券一次，权限撤销后不可打开通知。分发、人工核验及备注不改变提醒范围，通知不含券码。部署、调度及失败处理见[模块说明](exam-vouchers.md#到期提醒)。

### 状态与规则

只设置分发状态，使用核验作为记录信息，不另建兑换状态机：

| 状态维度 | 首版处理方式 |
| --- | --- |
| 分发状态 | 未分发、已分发 |

- 记录已分发不等于已兑换；人工核验的兑换情况也不代表已参加考试或考试通过。
- 适用考试/地区和有效期按代理商提供的信息记录，不推断额外业务规则；过期或作废情况通过备注记录，不增加首版状态。
- 使用情况以内部人员核验的凭证为依据，不宣称实时核销。

### 权限与敏感信息

考试券管理须有独立操作权限，不能因具备约考审核权限就默认获得考试券管理权限。由管理员通过现有权限配置授权，不将权限固定绑定到特定岗位；学员不通过本模块访问考试券或券码。

券码相当于兑换凭证，应加密存储；仅管理员配置为具有考试券管理权限的内部人员可按需查看完整券码，普通列表、操作记录和导出不包含完整券码。券码及操作记录暂不设单独清理期限，后续遵循组织数据保留政策。记录分发及状态变更操作。

### 底座能力应用示例

考试券模块的 CSV 导入沿用底座现有导入、字段校验和结果展示能力，不另建通用导入框架。公告模块示例中的通用导入流程会逐行处理并允许部分成功，与本模块“任一行错误则整批不导入”的业务约束不同，因此只在考试券业务流程内保证整批校验和写入的一致性，不为此改变底座通用导入语义。

分发、使用核验及导入等写操作接入底座操作审计配置，不在控制器或业务代码中重复写日志。审计只记录必要的动作和非敏感摘要，不记录完整券码、导入文件内容或其他兑换凭证；具体接入遵循[操作审计配置接入](operation-audit.md#配置接入)。

分发请求没有可安全采集的提交字段：接收人参数在审计采集时尚未验证，可能包含敏感内容，因此使用底座基础审计记录操作者、请求路径、券记录和结果；接收人保存在券记录中。

### 验收要求

1. 有考试券管理权限的内部人员可维护批次、导入和查询券记录；未获权限的用户不能通过页面或直接请求访问管理功能。
2. 券记录包含券码、代理商提供的适用考试/地区和有效期、所属批次及当前接收学员；同一券不能同时分配给多人，且不支持重新分发。
3. 内部人员可登记人工核验的使用情况，系统不依赖官方接口；使用情况不与约考记录关联。
4. 库存查询可区分未分发、已分发和已核验使用；到期前一个月向内部人员提醒。
5. 券码加密存储；普通列表、操作记录及导出不暴露完整券码。
6. 分发和状态变更可追溯操作记录；学员不能访问本模块。
7. CSV 批量导入任一行校验失败时，不导入该批次任何券，并报告错误行及原因。
8. 导入、分发及使用核验操作复用 GeminusAdmin 操作审计能力；审计内容不包含完整券码或导入文件内容。

## 模块关联

- 两个模块独立管理记录和权限，不能以考试券的管理状态代替官方预约事实、内部审核结论或资源占用状态。
- 首版不将考试券与约考记录关联；考试券分发和核验由内部人员独立管理。
- 预约凭证可作为考试券使用确认的依据，但核验官方预约和确认券使用是不同结论，不能自动互相替代。

## 管理方法与落实

采用成熟管理方法建立业务模型，再由考试机构条款、代理商合同和机构确认的运营政策确定具体规则。成熟方法说明如何管理，不替代业务决策；本文建议的状态名称和流程不能直接视为行业标准。

### 约考管理模型

借鉴运营管理中的有限容量排程和资源预约方法，采用“需求、资源承诺、官方事实分离”的模型：

- 学员申请表达考试需求，不代表已获得机构资源或官方考位。
- 资源占用表达机构的容量承诺，按考试时间考虑机位、人员及已有占用，不超出资源约束。
- 官方预约凭证表达外部已经发生的预约事实，与内部意向和资源安排分别记录。
- 内部审批不能替代官方预约，官方预约也不能自动证明机构资源可用。

[有限容量计划与排程](https://learn.microsoft.com/en-us/dynamics365/supply-chain/master-planning/planning-optimization/finite-capacity)可作为成熟 ERP 实践参考；只借鉴容量约束思想，不照搬制造业排程流程。

当前“提交即预占”是已记录的项目需求，不是有限容量理论必然要求。预占多久、是否超时释放及改期如何调整资源，仍须由机构明确政策。

### 考试券管理模型

借鉴库存管理与单件追溯方法，首版采用批次和单券记录管理，不建设通用库存或财务流程：

- 采购批次说明券从哪里来，以及适用的采购条款。
- 单券记录当前接收学员和分发状态，避免同一张券同时分配给多人。
- 内部人员通过凭证人工核验使用情况，不把分发状态当作兑换事实。

[库存预留与分配政策](https://learn.microsoft.com/en-us/dynamics365/supply-chain/inventory/reserve-inventory-quantities)仅作为批次和单件追溯的参考；考试券是兑换凭证，不直接等同于实物库存，也不照搬实物出入库规则。

### 业务规则依据

每条业务规则应能追溯到适用条款或机构确认的政策；字段、状态和页面操作只是规则的实现表达，不是规则来源。

| 规则 | 应有的依据 |
| --- | --- |
| 券适用考试、有效期、能否转让或恢复 | 代理商合同及发券方条款 |
| 官方改期、取消、重考限制 | 考试服务商政策 |
| 提交即预占，还是审核后占用 | 机构确认的运营政策；当前项目要求提交即预占 |
| 每名学员消耗多少机位及人员资源 | 实际考试组织方式和人员配置 |
| 谁能发券、核验、查看完整券码 | 机构授权及内部控制政策 |
| 状态名称、字段和页面操作 | 对上述规则的实现表达，不作为独立规则依据 |

授权、职责分离、操作留痕、凭证核验和定期对账，可参考 [GAO Green Book 内部控制框架](https://www.gao.gov/greenbook)的控制设计方法；这不表示本机构受美国联邦标准约束，也不默认增加审批层级。

流程表达可参考 [OMG BPMN 标准](https://www.omg.org/spec/BPMN/2.0.2)，明确参与者、审批节点、外部平台交互，以及取消、失败和异常分支。BPMN 不规定具体业务政策，也不要求引入流程引擎。

落实原则是用成熟管理方法约束模型，用外部条款和机构政策约束规则，用流程图与验收用例验证实现。不将系统扩展成 ERP，也不因其他系统存在某项能力就增加业务要求；缺少依据的规则保留为待确认项。

## 运行约束与非目标

- 独立应用的仓库名称、部署地址、数据库及应用配置尚未确定；复用底座或同一 Entra 身份来源不意味着与底座实例共用业务数据和账号授权。
- Azure 模型密钥通过部署配置管理，不写入仓库；接入前须明确机构隐私及数据处理要求。
- 本文不要求首版建设通用 API、独立客户端、M365 同步、成绩管理或志愿者管理。
- 实际实现应遵循底座的业务模块、安全和测试约定，优先使用底座能力；底座通用 Admin 模块不承载约考或考试券业务规则。
